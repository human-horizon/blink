# Строгая семантика оператора `?`

## Контекст

Parser уже представляет postfix `?` как `UnaryExpr{Op: "?"}`, но checker обрабатывает
его как неподдерживаемый unary operator. В Rust оператор требует `Try`-совместимый
операнд и совместимый тип возврата текущей функции.

## Цель

Реализовать проверку `?` для `Option<T>` и `Result<T, E>` в соответствии с доступной
моделью типов checker.

## Детали

- Хранить тип возврата текущей проверяемой функции в контексте checker.
- Для `Option<T>?` разрешать оператор только внутри функции, возвращающей `Option<U>`;
  тип выражения — `T`.
- Для `Result<T, E>?` разрешать оператор только внутри функции, возвращающей
  `Result<U, E2>` с совместимым типом ошибки; тип выражения — `T`.
- Для других типов выдавать диагностическую ошибку о необходимости `Try`.
- Не добавлять неявное преобразование `Option` в `bool`, `Tuple` в `Unit` или другие
  несовместимые типы.

## Тесты

- Валидный `Option<T>?` внутри функции, возвращающей `Option<U>`.
- Валидный `Result<T,E>?` с тем же типом ошибки.
- Ошибка при использовании `?` в функции, возвращающей обычный тип.
- Ошибка при использовании `?` над обычным типом.

## Приёмка

- [ ] Все тесты проходят с `GOMEMLIMIT=1GiB`.
- [ ] `go vet ./...` и `go build ./...` проходят.
- [ ] Bevy не получает новых wildcard-совместимостей.
- [ ] Число диагностик Bevy не увеличивается.
